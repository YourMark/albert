# 1.4.0 release-notes draft (accumulating)

Working draft, **not** the final `readme.txt`/`README.md` copy. Bullets are added
as each PR lands and are written against the actual diff (per the changelog
convention: plain site-owner language in the first sections, jargon only under
Developer). Version bumps and the real changelog happen on the release branch.

Theme: **Foundation + reliability**: day-one WordPress 7.1 support, kept lean and
clean, with everything degrading gracefully on 6.9/7.0.

---

**Features**

* New **Albert → Context** screen. Tell connected assistants what your site is
  and how to behave, your language, your tone, the words you use, and anything
  they must never touch, and see exactly what they receive. Switch off any
  detected section, colours and fonts, your content types, your shop info,
  that an assistant does not need.
* Assistants are now told where they are. Every conversation starts with your
  site's language and timezone, your theme's colours and fonts, which post types
  and taxonomies exist here, and your shop's currency and tax setting, so an
  assistant stops guessing and stops inventing brand colours that are nowhere on
  your site. Colours and fonts are only sent when your theme genuinely declares
  them; Albert never passes off WordPress's own defaults as yours.
* Assistants can now read Albert's task guides on their own. Previously these
  only appeared as commands you had to run by hand, so in practice they were
  never read. Each guide is listed by name at the start of a conversation, and
  only when it applies to your site.
* Text that comes from your site is now explicitly marked as information, not
  orders. Your instructions, your post content and your product descriptions all
  tell an assistant about subject matter and tone, they never change what it is
  allowed to do. That statement travels with every conversation.

**Improvements**

* Many of Albert's tools now carry a short note explaining the mistake that is
  easiest to make with them, the argument that has to be an array, the read that
  has to happen first, the image id that must not be changed. Assistants read
  these at the moment they use a tool, so it costs nothing until it helps.
* Every Albert screen now shares one visual language: the same cards, pills,
  switches and tables, in the same colours, instead of the older screens and the
  Abilities screen each having their own. Albert also picks up the admin colour
  scheme you chose in your WordPress profile, so it matches the rest of your
  admin instead of always being blue.
* A row of links across the top of every Albert screen shows where you are and
  lets you move between Albert's pages without going back to the sidebar.
* Several colours were too faint to meet accessibility guidelines: the outline
  around form fields, the off state of a switch, and the stripe on an
  information box. All are now dark enough to see clearly.
* On WordPress 7.1, the tool descriptions Albert sends a connected assistant are
  automatically tidied: internal, server-only details are removed before they go
  out. Cleaner and leaner, and it covers tools added by *other* plugins too, not
  just Albert's. On older WordPress, nothing changes.

**Developer**

* New `Albert\Context` module assembles the site context sent with the
  discovery response. `SiteContext` builds a structured array, the filterable API, and
  `PayloadRenderer` renders it to the compact labeled text block that is the wire
  format in the `discover-abilities` response. Every value passes through one
  choke point that strips embedded newlines and a leading `#`, so a theme.json
  palette slug or font name cannot forge a fake section into the payload. One
  renderer produces both the
  wire text and the Context screen's payload preview, and an integration test
  asserts they are byte-identical. New filters: `albert/context/enabled`,
  `albert/context/instructions`, `albert/context/sections`, `albert/context/site`,
  `albert/context/skills`. On WordPress 7.1 the discovery ability's output schema
  is extended to declare both fields, so a strict client cannot drop them.
* New `albert/skills/registry` filter registers a skill as data: `slug`,
  `summary`, and either `file` or `body`, plus declared preconditions
  (`woocommerce`, `block_editor`, `classic_editor`, `multisite`, or a `when`
  callable). A skill lists in the discovery response only when its preconditions hold;
  an unrecognised condition fails closed. The index is memoised per request; one
  screen render read it four separate times before this, running the filter
  once for each.
* New read-only `albert/get-skill` ability returns one guide's Markdown body by
  slug, gated on `edit_posts`. MCP prompt registration is unchanged and stays
  alongside it.
* `Core\Annotations` factories now take an optional `instructions` string,
  surfaced as `meta.annotations.instructions` and returned verbatim by
  `get-ability-info`. 25 abilities carry one.
* The Context screen shows what is sent (a byte-for-byte preview) but not a
  token cost. It shipped one first, script-aware rather than characters ÷ 4,
  calibrated against `o200k_base` with a stated error band, but different
  assistants tokenise differently, so any number could only ever be shown with
  a wide, provider-specific error band attached, and it did not change what an
  owner should do: the section descriptions already say what each one
  includes, which is what a decision to switch one off actually needs.
  Removed rather than kept as decoration. The measurement behind the earlier
  "no budget ceiling" decision still holds, on a real site the context block
  is a small fraction of the discovery response, nothing observable happens at
  any number worth drawing a line at.
* The design system drops its dark palette. It was declared behind a selector
  nothing set, so ~64 values shipped that no browser rendered and no test could
  check. WordPress has no dark admin scheme; dark becomes a project when there is
  a trigger to verify it against.
* One info control for the whole plugin. `assets/src/shared/InfoPopover.jsx` is
  what every React screen renders, built on core's `Dropdown`; its styles moved
  from `admin-abilities.css` into the primitives as `.albert-info`. Server-rendered
  screens keep a CSS-anchored equivalent, now `.albert-tip` (from
  `admin-settings.css`, positioned in CSS rather than by script). The split is by
  rendering context, not by screen.
* New `__text` wrappers on the page header, card header and toggle row, the
  element those two-child flexes need when a header carries a title, a
  description *and* a control.
* Removed: the `.albert-switch` primitive, before it shipped. Albert's screens
  use `FormToggle` from `@wordpress/components`, the control the Abilities screen
  was already built on. The design system's existing rule for buttons ("if core
  ships it, Albert does not draw its own") applies to switches too, and having
  both meant two Albert screens in the same menu showed switches at 40x22 and
  32x16. The `notice-accent` token also goes, along with the thick coloured edge
  it coloured: `.albert-hint` now carries tone as a surface tint and a hairline.
* Stylesheets are versioned on the file's modification time rather than
  `ALBERT_VERSION`. Version bumps happen only in release branches, so every CSS
  change since 1.3.1 has shipped under a version string already in the browser
  cache, and the design system may never have fully rendered during development.
  `Admin\Assets::version()` is the shared resolver, with the constant as
  fallback.
* `albert/get-skill` uses the `site` ability category, which Albert now registers
  defensively alongside `user`. Core ships both as built-ins, but they are absent
  in the WordPress test environment, where the ability silently failed to
  register.

* Upgraded the bundled MCP adapter to 0.6.1 (from 0.5.0). The adapter now depends on
  `automattic/jetpack-autoloader`, disallowed in `config.allow-plugins` because Mozart
  owns dependency scoping; it is rewritten under `Albert\Vendor\` and stays inert.
* Client-facing JSON Schema preparation on WP 7.1: outgoing MCP tool schemas pass
  through `wp_prepare_json_schema_for_client()` at `tools/list` and `get-ability-info`,
  gated by the new `Albert\Support\WpCompat`; canonical schemas are untouched and
  pre-7.1 is a pass-through.
* `AbilitiesRegistry::is_mcp_public()` adopts the `meta.mcp.public ?? meta.public ??
  false` exposure precedence (matching WP 7.1 / mcp-adapter 0.6.0). `meta.public` is
  the forward-looking flag; `meta.mcp.public` is retained for backward compatibility.
* New `AbilitiesRegistry::get_all_raw()` reads `WP_Abilities_Registry::get_all_registered()`
  directly. WordPress 7.1 runs `wp_get_abilities_item_include` / `wp_get_abilities_result`
  even on a bare `wp_get_abilities()` call, so Albert's bookkeeping paths (the disabled-list
  enforcement, the new-ability reconcile, the fresh-install default, the Abilities screen
  payload and the dashboard count) moved onto the raw registry. A third-party filter can no
  longer make Albert lose track of an ability that is still registered and still executable.
* New `albert/abilities/invoked` action, relayed from WP 7.1's `wp_ability_invoked` by
  `Albert\Core\InvocationRelay`. Fires for every ability invocation whatever the outcome,
  including denied, invalid and short-circuited calls, and abilities Albert does not own.
  No consumers in Free; this is the seam the Premium activity log binds to. Inert below 7.1.
* New `WpCompat::supports_execution_lifecycle()`, detecting the 7.1 execution lifecycle
  (`wp_ability_invoked`, `wp_pre_execute_ability`, `wp_ability_validate_input` / `_output`,
  `wp_ability_execute_result`) via the 7.1-only `WP_Filter_Sentinel` class.
* Audited every ability schema for `validate_callback` / `sanitize_callback` / `arg_options`,
  which the Abilities API never invokes: zero occurrences. `AbilityContractTest` now asserts
  this on every registered ability, at any schema depth, so it stays true.
* CI integration matrix gains a `trunk` row for WordPress 7.1 coverage through RC and GA.
* CI's PHPStan job now derives which build assets to stub from the source rather
  than naming one by hand. A second admin screen's build artifact silently broke
  static analysis, passing locally only because the real build existed there and
  PHPStan's result cache masked the failure.
* New design system. `assets/css/albert-tokens.css` (handle `albert-tokens`) is the
  single source of colour, spacing, type, radius and motion, in `oklch()`;
  `assets/css/albert-primitives.css` (handle `albert-primitives`, depends on the
  tokens) holds the shared components. `Admin\Assets` registers both;
  `Admin\Menu` owns submenu ordering and renders the page navigation as real
  links with `aria-current="page"`. Add-ons declare `albert-primitives` as a
  stylesheet dependency; see the contract table in `.claude/CLAUDE.md` and the
  full reference in `docs/design-system.md`.
* Breaking for add-ons: the 56 value-named custom properties `admin-settings.css`
  declared (`--albert-primary`, `--albert-font-lg`) are replaced by role-named
  ones (`--albert-color-accent`, `--albert-font-size-section-title`) with **no
  alias layer**. `albert-premium-service` 1.2.0 ships the matching migration and
  must be released alongside this version.
* `--albert-color-accent` is declared on `body`, not `:root`: WordPress sets the
  scheme colour on the body class while `:root` carries only a base default, so
  resolving the `var()` at `:root` captures the default and inherits it everywhere.
